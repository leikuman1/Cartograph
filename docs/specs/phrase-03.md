# 阶段 3 — 解析器

目标。 将磁盘上的代码仓库转换为文件列表及文件之间真实的连接关系，并能够证明解析结果是正确的。

## 构建内容

- 遍历代码仓库：决定哪些文件成为节点、统计行数、计算内容哈希，以及确定每个文件所属的模块。
- 使用真正的 TypeScript 解析器读取每个文件中的导入，并将三种类型的导入转换为边：普通导入、重新导出，以及使用字符串字面量的动态导入。
- 入度（Fan-in）和出度（Fan-out），在移除重复边之后，根据边列表计算。
- 覆盖率（Coverage）。 对每一个发现的导入：它是解析到了仓库内部的文件、指向仓库外部、被有意排除，还是解析失败——如果失败，原因是什么。不仅要统计失败数量，还要保留失败的具体示例。
- 适配器接口，以及不对任何框架作出假设的默认回退适配器。
- 一个能够针对指定目录运行解析器的命令，打印解析结果，并可以将完整结果写入具有类型定义的数据文件。此后构建的所有功能都将读取这一输出，因此它所写入的数据结构就是一份契约。

## 约束条件

- 这部分代码不得导入任何 Web 框架、UI 库或数据库客户端。它接收一个目录路径，返回数据，并且可以通过普通脚本运行，无须启动任何其他服务。
- 它必须能够针对磁盘上的任意目录运行，包括当前项目。解析器本身不获取任何内容——不发起网络请求、不访问 URL，也不在内部克隆仓库。它只接收一个路径。仓库是如何被放到磁盘上的，不是它需要关心的问题，因此可以自行克隆任何需要用于测试的仓库。
- 其中任何地方都不得包含针对特定框架的检查。本阶段唯一涉及框架知识的部分，是完全不包含任何框架知识的默认回退适配器。
- 文件选择必须基于结构。 从入口点开始，沿依赖关系向外遍历，或者保留完整目录。绝不能按照代码行数选取最大的 N 个文件——这种做法会保留某个文件，却丢弃它所导入的叶子文件，从而产生指向不存在节点的边。这种问题在小型演示仓库中永远不会显现。
- 无法解析的导入必须被报告为未解析（unresolved），并附带原因。绝不能悄悄丢弃，也不能猜测其指向。在仓库内容和解析配置相同的情况下，失败原因不得因文件处理顺序、解析缓存命中或祖先目录的附带探测而改变；只依据该导入实际选中的本地候选路径判断。

## 验收检查

运行以下测试并报告具体数字。 全部在终端中完成，全部由你自行执行。

1. 针对当前项目运行解析器。报告发现的文件数、已解析的文件数、跳过的文件数，以及每个文件被跳过的原因。这三个数字必须满足相应的加总关系，并且不能有任何文件在未说明原因的情况下被跳过。
2. 输出中的每个文件都必须包含其所属文件夹。对于一个包含几百个文件的仓库，不同文件夹的数量应该达到几十个，而不是寥寥几个。此后构建的所有功能都将根据这个值进行分组，因此如果这个值缺失或粒度过粗，就会破坏所有下游结果。
3. 克隆一个使用桶文件（barrel files，集中重新导出文件）的仓库并进行解析。报告发现的重新导出数量与成功解析的重新导出数量。这两个数字必须一致，否则每一个差额都必须有明确的原因。
4. 将某个被导入的文件重命名，然后重新运行。应当恰好出现一个未解析的导入，并且输出需要说明原因。
5. 将输出写入文件，再重新读取。类型约束必须仍然成立。

## 本阶段不包括

除默认回退适配器之外的框架适配器。`require()`。此外，本阶段还不进行任何渲染：这一阶段在终端中结束，而这正是其设计意图。
