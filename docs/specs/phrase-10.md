# 阶段 10 — 解释、缓存与追踪（Explain, cached and traced）

目标。 实现第一次模型调用，并确保围绕它的所有必要条件都得到满足。

## 构建内容（Build）

- 整个代码库中只有一个地方负责创建 AI 客户端，并对其进行封装，使通过该客户端发起的每一次调用都受到追踪。
- 解释文件（Explaining a file）：根据文件真实的相邻依赖关系生成解释——包括它导入的所有文件，以及所有导入它的文件，并将这些信息全部提供给模型。
- 解释折叠后的文件夹（Explaining a folded folder）：这是一个不同的问题——这个文件夹里有什么，以及为什么有这么多依赖关系指向它。
- 为适配器无法识别的文件分配角色。
- 为上述两种解释建立缓存，缓存键根据被解释对象的内容生成。
- 已经获取过的解释必须保留在详情面板中。 切换到其他对象，再切换回来，原来的解释仍然存在，无需再次点击。用户感受不到的缓存，就不算真正的缓存。
- 渲染解释内容。 Prompt 只允许使用三种格式——行内代码、项目符号列表和粗体——不允许使用标题，因为详情面板很窄，标题会把几个简短的段落切割成带标签的碎片。正确渲染这三种格式，并将解释文本中出现的每个仓库文件路径转换为可点击的链接，点击后能够在地图上定位到对应位置。
- 过期状态（Staleness）。 将每个已解释文件存储的内容哈希与仓库中的实际文件进行比较。如果文件已经发生变化，或者仓库已经更新到分析时所记录的提交之后，就明确告知用户，并提供重新分析的选项。

## 约束条件（Constraints）

- 模型可以解释文件和分配标签，但不能决定两个文件之间是否存在依赖关系，也不能自行遍历图谱。模型看到的每一条文件路径，都必须是事先提供给它的。
- 缓存读取必须发生在被追踪的调用内部，而不是调用之前。缓存命中必须在 Trace 中表现为一条已记录的运行，并且其中没有模型调用——否则就无法区分缓存确实正常工作，还是缓存已经失效。
- 模型版本必须精确固定，绝不能使用会动态变化的别名，而且模型名称必须成为缓存键的一部分。重新固定某个模型版本时，只会使该模型对应的缓存失效。
- 分类只能返回非结构性角色。模型可以将文件标记为 service、repository、model、util、config、component 或 hook，但绝不能标记为 page、route 或 controller——这些角色会决定路由表和入口文件的颜色，因此必须由框架约定来识别。
- 不要完全禁止格式化，然后直接输出模型返回的内容。模型无法始终可靠地遵守格式要求，结果可能是反引号被直接显示为反引号——也就是输出了 Markdown，却没有对应的渲染器。允许一个有限的格式子集，并正确渲染它，才是能够在实际使用中可靠工作的方案。
- 如果没有配置 Tracing，模型调用仍然必须能够成功。并且需要在某个位置明确显示追踪未配置的状态，因为否则缺少 API Key 的情况，看起来就会与配置正常但尚未产生任何流量的情况完全一样。

## 验收检查（Acceptance check）

1. 对一个文件点击 Explain（解释）：出现一段结合其真实相邻依赖关系、描述该文件作用的文字。解释中提到的文件确实与它存在依赖关系，点击其中任意一个文件名，都能将地图定位到对应文件。
2. 渲染结果中不能出现任何多余的反引号、星号或井号。
3. 再次点击 Explain：结果立即出现。然后打开 Tracing 控制台——两次运行记录都存在，而且第二次记录的 Token 消耗为零。
4. 解释一个折叠后的文件夹。回答必须围绕整个文件夹，而不是只总结其中某一个文件。
5. 向已分析的仓库推送一个新的 Commit，重新加载页面，然后对你修改过的文件点击 Explain。界面应当提示该解释已经过期，并提供重新分析的选项。
6. 找到一个没有被任何适配器识别的文件。它应当获得一个合理的角色，而且该角色不能是可路由访问的角色。
