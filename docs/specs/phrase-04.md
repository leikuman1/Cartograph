# 阶段 4 — 画布（The canvas）

目标。 将解析器刚刚生成的结果绘制成屏幕上的地图。

## 构建内容（Build）

- 对磁盘上的一个真实代码仓库运行解析器，并将其输出作为一个带类型的数据文件提交到项目中。这是临时搭建的基础设施——它的存在是为了让界面能够在没有账户、数据库或网络的情况下完成开发。一旦分析结果得到妥善存储，它就会被移除。
- 选择一个足够大、值得可视化的仓库。 应当包含几百个文件，具有真实的目录嵌套结构，以及几个被大量其他文件依赖的文件夹。一个只有二十个文件的仓库，会让折叠功能看起来正常工作，即使它实际上根本没有得到充分测试。
- 不要为了适应画布而改变解析器的输出结构。 如果画布需要不同的数据结构，就从原始输出中派生。解析器的输出结构是约定好的契约；如果在这里改变它，就意味着之后在其他所有地方也必须跟着改变。
- 创建一个预览路由，通过真实的界面渲染这些数据。
- 在这一阶段确定界面整体布局，之后不再重新调整。 三栏布局：左侧是一条狭窄的侧边栏，中间是占据主要空间的地图，右侧是详情面板。后续阶段只会填充这些区域，不会移动它们。
- 左侧边栏列出文件类别——每个类别包含一个颜色标记、名称，以及该类别中的文件数量。现阶段点击类别不会产生任何效果。
- 折叠（Folding），这是整个地图所依赖的核心规则。 每个目录最初都是一个独立节点。然后，从最深层的目录开始向上处理，将包含文件数量少于几个的目录合并到其父目录中。如果这样处理后，节点数量仍然多到无法阅读，就提高阈值并重新执行，直到找到能够将节点数量控制在大约二十几个以内的最低阈值。仓库自身的结构决定折叠深度，不预先指定任何深度。
- 点击一个折叠节点会将其展开。
- 展开后的文件夹会变成一个面板，而不是一堆分散的节点。 它在画布上仍然是一个整体对象——一个带边框的盒子，其标题栏显示文件夹名称、包含的文件数量，以及扇入（fan-in）和扇出（fan-out）。文件则以行的形式显示在盒子内部。当文件行数超过可显示的数量时，面板会显示还有多少行未展示，而不是无限增大。连接边指向这些文件行。
- 节点的高度表示有多少对象依赖于它。宽度由标签决定，因此较长的名称不会让一个文件看起来更重要。
- 展开文件夹时，重新调整视图，使新展开的面板能够完整显示。
- 点击已展开面板的标题栏，会将其重新折叠为单个节点。
- 面板内的文件行与普通节点一样，都可以被选中。 选中任意一个后，该对象、与其相连的边，以及这些边连接到的所有对象，都保持完整的视觉强度，其余所有对象则变暗。
- 布局必须是确定性的。相同的数据每次都应生成相同的图形。

## 约束条件（Constraints）

- 折叠操作必须从最深层开始，每一轮都要重新计算，因此同一深度上的某次合并不会影响其他合并操作所看到的内容。
- 标签必须使用在当前屏幕显示范围内仍能保证唯一性的最短名称。
- 右侧详情面板在这一阶段作为一个空白列存在。它不是模态框、抽屉或覆盖层，而且后续不会被重建或重新定位。
- 展开时重新调整视图，只允许缩小，绝不允许放大。 否则，为了适应新展开的面板而调整视图，可能会放大并聚焦到该面板，导致图中的其他部分消失。此外，由于视图调整依赖展开状态，很容易错误地根据状态变化之前、而不是之后的状态来计算适配范围。

## 验收检查（Acceptance check）

统计以下项目并报告具体数字。不需要浏览器，也不需要主观判断。

1. 节点数量应控制在大约二十几个以内，并且大致处于每十个文件对应一个节点的水平。
2. 每个节点都必须包含不止一个文件。如果出现单个文件作为独立节点，就意味着折叠规则没有被实现，因为按照该规则不可能产生这种结果。
3. 每条连接边的终点都必须是一个实际存在的节点。

然后是我的两项检查，每项只需要五秒钟：

4. 点击一个折叠节点。它会展开，将文件以行的形式显示在节点内部，标题栏显示文件数量，连接边重新连接到这些文件行，点击标题栏又会将其折叠回去。如果点击后没有任何反应，那么无论前面的统计数字如何，这一阶段都不能算完成。
5. 图形应充分利用画布空间，而不是挤在某个角落；标签应当在不需要缩放的情况下就能清晰阅读。
