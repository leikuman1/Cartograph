# Phase 2 — 仪表盘与数据库结构

目标： 工作空间已经建立，归属于某个团队，并且系统能够证明这一归属关系。

## 一、需要实现的功能（Build）

\- 首次数据库迁移（Migration）

- 创建 8 张数据表：
  - `projects`：项目
  - `analyses`：分析任务
  - `files`：文件
  - `edges`：边（关联关系）
  - `routes`：路径
  - `explanations`：解释
  - `file_roles`：文件角色
  - `insights`：洞察
- 每张表都通过指向组织（Organization）的外键，明确其数据行的归属。
- 删除组织时，与其关联的数据也会被级联删除。

\- 行级安全策略（Row-Level Security，RLS）

- 为全部 8 张表启用行级安全控制。
- 权限控制必须通过数据库策略实现。
- 策略的判断条件从身份认证 Token 中读取组织声明（Organization Claim）。

\- 仪表盘（Dashboard）

- 展示当前所属组织的分析任务列表。
- 显示每个分析任务的当前状态。
- 如果某个团队从未执行过分析任务，显示空状态页面（Empty State）。

\- 初始化测试数据（Seed Data）

- 由于目前还没有实际创建分析任务的功能，因此需要预先插入一些测试数据。

## 二、约束条件（Constraints）

### 1. 权限控制必须由数据库负责

授权（Authorization）应该是数据库自身具备的能力，而不是依赖应用程序主动执行权限检查。

任何数据表如果没有配置对应的安全策略，就不允许被读取。

### 2. 数据库迁移必须纳入版本控制

数据库结构变更必须通过迁移文件（Migration Files）管理，并提交到 Git 等版本控制系统。

不能直接在数据库管理界面中手动修改结构。

### 3. 仪表盘不能在应用代码中按组织过滤数据

仪表盘不应该通过应用层代码过滤组织数据。

如果数据库查询返回了其他组织的数据，那么问题出在数据库的行级安全策略，而不是应用程序缺少过滤逻辑。

### 4. 切换组织不应该改变查询逻辑

用户切换当前组织后，同一个页面展示的数据应该随之改变。

不需要为不同组织编写不同的数据库查询。

## 三、验收标准（Acceptance Check）

1\. 验证组织之间的数据隔离

为两个不同的组织分别插入分析任务测试数据。

验证以下行为：

- 登录第一个组织后，仪表盘只显示该组织的数据。
- 切换到第二个组织后，仪表盘显示的数据随之改变。
- 整个过程中，应用程序没有通过修改查询逻辑或查询不同的数据表来实现数据切换。

2\. 验证全部数据表的行级安全策略

确认全部 8 张数据表都已启用 Row-Level Security（RLS）。

必须逐一检查全部 8 张表，不能只抽查其中几张。

## 四、本阶段不包含的内容（Not in this phase）

「分析代码仓库（Analyse a Repository）」表单。

目前还没有实现能够处理该表单请求的后端功能，因此暂时不添加这个表单。

一个长期无法实际执行操作的按钮，比完全没有这个按钮更糟糕。
