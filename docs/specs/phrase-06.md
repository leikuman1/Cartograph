# 阶段 6 — 图计算、侧边栏与洞察

目标。 在完全不涉及任何模型的情况下，让这个工具真正变得实用。

## 构建内容（Build）

- 影响范围（Blast radius）——如果这个文件发生变化，所有会受到影响的对象。依赖链（Dependency chain）——这个文件所依赖的所有对象。两者本质上都是对边列表进行相同的传递性遍历，只是方向参数不同，并且都有深度限制。只实现一次。
- 默认遍历两层深度。再深入就会返回仓库中的大部分内容，从而失去作为答案的意义。
- 两者都以按钮的形式出现在详情面板中，并且都能立即返回结果。
- 洞察（Insights），共四种，全部基于边列表中的事实：循环导入、没有任何文件导入的文件、被异常多的对象导入的文件，以及长度过长的文件。
- 左侧边栏开始具备实际功能：点击一个类别时，不属于该类别的所有对象都会变暗，而不是被移除。每个已展开的面板都会显示其中有多少文件匹配该类别，这样你就能在不丢失整个仓库结构的情况下，看出该类别分布在仓库的哪些部分。

## 约束条件（Constraints）

- 这一阶段完全不涉及任何模型。既不用模型发现洞察，也不用模型描述洞察。每条洞察的描述语句都来自四个固定字符串之一。
- 环检测必须使用迭代方式，而不是递归方式。真实的代码仓库可能会导致调用栈溢出。
- 没有任何文件导入的文件，并不自动意味着它是孤立文件。 页面、路由、布局、中间件和配置文件是由框架访问的，而导入关系图本来就无法体现这一点。如果将它们报告为未使用文件，就相当于解析器把自身视野的局限性描述成了代码本身存在的问题。
- 洞察显示在一个初始处于折叠状态的面板中，绝不能成为用户首先看到的内容。这个产品的目的是解释代码库，而不是给代码库打分。
- 没有任何文件导入的文件排在列表首位。对于这个产品的目标用户来说，这类洞察具有解释作用。循环导入和文件过长则更接近一种评判，因此放在下面。

## 验收检查（Acceptance check）

1. 选择一个文件，点击 Blast radius（影响范围）：列表立即出现，没有加载指示器，也没有网络请求，而且结果正确——打开其中两个条目进行抽查。
2. 选择一个你知道没有被任何文件导入的文件。它应该出现在洞察面板中。然后选择一个同样没有被任何文件导入的页面或路由文件。它不应该出现在洞察面板中。
3. 洞察面板能够在已提交到项目中的代码仓库里发现一个真实的循环依赖，并且通过手动沿着依赖关系检查，能够确认这个循环确实存在。
4. 点击侧边栏中的一个类别：其他所有对象都会变暗，但仍保留在屏幕上，并且各个面板中的匹配数量相加，应当等于侧边栏显示的数量。
5. 这一阶段的任何操作都不会产生网络请求。打开浏览器的网络面板，将所有可点击的内容都点击一遍，检查一次。
