# 阶段 8 — 框架适配器（Framework adapters）

目标。 让应用程序能够识别它正在分析的是哪种类型的代码库。

## 构建内容（Build）

- 一个用于 Next.js 的适配器——根据路径约定识别文件角色，并从这些路径中推导出路由。
- 一个用于 NestJS 的适配器——根据文件名后缀识别文件角色，并结合控制器和方法上的装饰器构建完整路由。
- 一个用于 React 的适配器。在 Next.js 适配器完成后，实现它几乎不需要额外工作。
- 提取路由，将其存储并以表格形式展示。
- 左侧边栏根据框架自动调整：NestJS 仓库显示 Controllers、Services、Modules、Entities；Next.js 仓库显示 Page routes、API endpoints、Server actions。

## 约束条件（Constraints）

- 路由要么完全准确，要么不存在。 只有当 HTTP 方法和完整路径模式都能直接从解析后的语法中恢复，且不需要任何推断时，才生成路由。如果其中任何一个需要猜测，就不显示任何内容。错误的路由路径与凭空编造的依赖边一样，都是不可接受的。
- 框架检测按照固定顺序执行，匹配到的第一个结果优先。如果仓库没有匹配任何框架，也必须能够正常渲染，使用通用文件角色，并显示一个空的路由表格。
- 侧边栏的分类体系与适配器本身分离，这样浏览器组件就可以读取类别名称列表，而不必将解析器和文件系统库打包到浏览器端。
- 类别名称必须是具体的角色名称，而不是抽象概念。阅读 NestJS 仓库的人想看到的是“Controllers 4”，而绝不是“Entry points 4”。
- 侧边栏的顺序按照阅读顺序排列，并且保持固定——首先是可路由访问的入口，然后是它们背后的各个层次，最后是底层基础设施。同一个仓库始终以相同的位置顺序展示各个类别。

## 验收检查（Acceptance check）

1. 分析一个 Next.js 仓库：左侧边栏显示 Page routes、API endpoints、Server actions，并且数量统计正确。
2. 分析一个 NestJS 仓库：左侧边栏显示 Controllers、Services、Modules，并且路由表格显示 HTTP 方法和完整路径模式。
3. 从路由表格中打开三个路由，手动确认它们的 HTTP 方法和路径都与代码完全一致。
4. 分析一个没有匹配任何适配器的仓库——它能够正常渲染，文件角色使用通用分类，路由表格为空，而不是显示错误内容。
5. 在解析器核心代码中搜索“nextjs”。这个词只出现在适配器中，其他地方均不出现。
