# 阶段 7 — 流水线（The pipeline）

目标。 粘贴一个 URL，然后看着你自己的代码仓库变成一张地图。

## 构建内容（Build）

- 以归档文件的形式获取公开代码仓库。不请求任何仓库访问权限，也不存储任何令牌。归档中的普通符号链接和硬链接不创建、不跟随，保留路径及跳过原因并计入覆盖率，继续分析其余文件。危险路径、重复或冲突条目、特殊设备和损坏归档仍然失败；不支持的特殊条目错误须说明路径和类型。
- 记录归档文件对应的提交（commit）。后续阶段需要知道仓库自那次提交以来是否发生了变化。
- 整个运行流程：获取、选择、解析、存储——每个阶段都有明确的名称，并在最外层设置异常捕获，将状态写为失败，而不是让某条记录永远卡在解析过程中。
- 将仪表盘上的表单最终连接到实际功能。
- 每个仓库只对应一条分析记录。 提交一个已经分析过的仓库 URL，不会创建第二条分析记录，而是将你带到现有的分析页面。重新运行同一个仓库的分析，必须从该分析页面主动触发，而不是再次粘贴 URL 就自动执行。
- 一个实时更新的进度页面，在每个阶段进行时显示其名称。
- 代码浏览器现在读取真实存储的数据行，而不是提交到项目中的数据文件。
- 在地图上添加一个覆盖率横幅，当图谱不完整时明确说明这一点。

## 约束条件（Constraints）

- 实时进度由数据库驱动，而不是通过浏览器轮询实现。当阶段发生变化时，数据库中的某个机制负责发布更新，页面则订阅这些更新。发布阶段名称及其消息，而不是整条记录——这样页面就不需要进行任何过滤或解释。
- 在任何内容能够发布到频道之前，必须先声明该频道。 每条分析对应的频道模式，需要作为数据库迁移的一部分，与数据表一起注册。向未注册的频道发布消息会悄无声息地失败，表现出来的症状就是进度页面始终不更新。
- 通过我们自己数据表上的触发器发布消息。绝不要在实时通信机制本身的表上附加触发器。
- 谁能够订阅频道，同样由策略控制。 其他组织的分析频道不能被订阅，原因与不能查询其数据行相同。进度流必须受到与数据相同的权限保护。
- 浏览器端使用经过身份认证的客户端，而不是未经认证的普通客户端——它需要访问令牌 Cookie 才能建立 Socket 连接，这也正是该 Cookie 被设置为可读取的原因。
- 运行失败时，必须记录失败的原因以及失败发生的阶段。
- 运行进程意外终止但没有记录失败的情况，也必须能够被识别。 这里没有队列或超时机制，因此，如果进程在解析过程中停止，就会留下一条永远显示“parsing”的记录。仪表盘会将超过几分钟仍未完成的运行标记为过期（stale），这样无需打开记录，也能清楚地区分正在运行的任务和已经中断的任务。
- 覆盖率横幅可以折叠，但折叠后必须保留一行文字，并且仍然显示具体数值。一个实际上只有 30% 完整度的图谱，绝不能悄无声息地看起来像是完整的。
- 在这一阶段删除已提交到项目中的解析器输出文件和预览路由。 它们只是为了构建界面而设置的临时基础设施；现在分析结果已经得到妥善存储。之前基于这些临时数据构建的所有功能，都必须继续在真实数据上正常工作。

## 验收检查（Acceptance check）

1. 粘贴一个公开代码仓库的 URL。各个阶段以真实的名称依次推进，而不是只显示一个加载动画，最终进入该仓库的地图页面。
2. 粘贴一个已经分析过的仓库 URL。你会进入现有的分析页面。该仓库仍然只有一条分析记录，而不是两条。
3. 粘贴一个不存在的仓库 URL。运行会失败，并显示说明出错原因的消息；仪表盘中的对应记录显示为 failed，而不是永远停留在“parsing”状态。
4. 在分析运行过程中，用第二个标签页打开仪表盘。该页面中的阶段也会实时更新，无需刷新。
5. 分析一个特意设置得比较复杂的仓库——例如使用路径别名，或者包含嵌套应用——并确认覆盖率横幅出现，且显示一个低于 95% 的数值。

## 不属于本阶段的内容（Not in this phase）

框架特定的角色，以及路由。
