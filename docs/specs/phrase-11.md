# 阶段 11 — 评估（Evals）

目标。 让回答质量不再只是主观评价，而是变成可以量化的数值。

## 构建内容（Build）

- 提供一种方式，让 Web 应用之外的脚本也能够加载相同的环境配置。
- 虚构路径检查（Invented-path check）。 提取解释文本中每一个看起来像文件路径的文本片段，并将其与模型实际看到的文件路径集合进行比较。任何不属于该集合的路径都被视为虚构。将这一检查作为实时评估器，对真实流量进行评估，而不只是针对保存的数据集运行。
- 角色准确率（Role accuracy）。 框架约定已经能够为某些文件分配确定的角色，而这些文件在正常运行时根本不会交给模型处理——因此，它们构成了一个拥有真实标准答案的留出数据集。隐藏文件角色，让模型进行分类，然后比较结果。
- Prompt 版本（Prompt versions）。 使用当前版本的解释 Prompt 和之前的一个版本，在同一个数据集上运行两组独立实验，并对它们的评分进行并排比较。

## 约束条件（Constraints）

- 虚构路径检查必须使用确定性代码实现，而不是让一个模型给另一个模型打分。这只是集合成员关系判断，具有精确的答案。一个自身也会产生幻觉的幻觉检测器毫无价值。
- 角色评估数据集只能包含那些能够通过框架约定确定角色，且该角色属于分类器允许返回的类别的文件。如果拿模型被禁止回答的问题来给它评分，那么这样的评估毫无意义。
- 已弃用的 Prompt 应当保存在评估代码中，而不是应用程序中。仅仅为了让测试能够访问一个已经废弃的 Prompt，就将它保留在正式应用中，意味着测试反过来影响了产品设计。
- Prompt 版本比较确实不可避免地需要使用模型作为评判者——“这个解释是否足够具体、能够真正帮助用户”并没有精确答案。必须明确说明这一点，而不是把评估数值呈现得比实际更客观、更确定。

## 验收检查（Acceptance check）

1. 对近期真实生成的解释运行虚构路径检查。检查应当报告一个分数，并且它标记出的任何失败案例，都能够在十秒钟内通过人工检查确认。
2. 向检查器输入一段人为插入了虚构文件名的解释。检查器应当能够识别它。
3. 运行角色准确率评估。它应当基于一个至少包含 30 个文件的数据集，返回一个百分比。
4. 两个 Prompt 版本及其评分应当在控制台中并排显示，并且你能够说清楚哪个版本更好，以及好多少。
